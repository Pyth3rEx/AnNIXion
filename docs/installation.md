# Installation

Choose the path that matches your starting point: install from the AnNIXion ISO, or add AnNIXion to an existing NixOS system.

## Option A: Fresh install from the ISO

This is the recommended option. You don’t need an existing NixOS installation.

### 1. Download the ISO

Download the latest `AnNIXion-vX.Y.Z.iso` from the [GitHub Releases](https://github.com/Pyth3rEx/AnNIXion/releases) page.

### 2. Create a bootable USB

On Linux or macOS, write the ISO to a USB drive:

```bash
sudo dd if=AnNIXion-*.iso of=/dev/sdX bs=4M status=progress oflag=sync
```

Replace `/dev/sdX` with the USB device—not a partition on it. This command overwrites the selected device. On Windows, you can use [Rufus](https://rufus.ie).

### 3. Boot the installer

Boot your computer from the USB drive. The live system logs in as `operator` and starts the `annixion-install` TUI. The live installer login is `operator` / `operator`.

### 4. Connect to the network and start the installer

The installer clones AnNIXion over the network. If it exits because it can’t connect, connect first and then run it again:

```bash
nmtui
annixion-install
```

`nmtui` opens a text interface for connecting to Wi-Fi or configuring Ethernet.

### 5. Choose or provide your configuration

The wizard can create a new configuration from your answers. If you already have an AnNIXion `user/` configuration, copy it to a USB drive for the installer to find, or pass it directly:

```bash
annixion-install --user-config /path/to/user
```

You can also provide a Git URL. If the configuration was generated by this release, or a compatible one, and is set up to skip the wizard, the installer uses it as-is. Otherwise, its values become the wizard’s defaults. The configuration is validated before the installer touches the disk.

To install a branch other than the repository’s default branch:

```bash
annixion-install --branch dev
```

### 6. Complete the wizard

The wizard asks for the settings that go into `user/configuration.nix` and `user/home.nix,` including:

- Hostname, account username, and password. The username defaults to `operator`; you can choose another.
- Timezone and keyboard layout.
- Which of the four Firefox profiles to build.
- Desktop compositing.
- Whether to enable optional example configurations, such as the HTB networking helper, Git identity, and Zsh aliases. See `user/README.md`.
- A nixpkgs cooldown policy: use the repository default, the newest stable release, a specific release, a chosen number of releases behind the newest, or a fixed number of days old.

The cooldown policy lets you pin nixpkgs to an older point rather than immediately using the newest available release. If you enable the Git identity example, the wizard asks for a name and email address.

By default, SysReptor uses the same username and password as the OS account. You can instead choose a separate SysReptor login.

The installer requires UEFI boot and does not support legacy BIOS/CSM. To check whether the live system booted in UEFI mode:

```bash
ls /sys/firmware/efi
```

Check this before starting the installation: the installer cannot complete a legacy-BIOS installation.

### 7. Review and start the installation

The installer resolves the selected nixpkgs cooldown pin against GitHub and updates `flake.lock` before doing anything to the disk. If there’s no network, or GitHub is unreachable or rate-limited, it falls back to the repository’s default pin with a warning. Once you have a connection, you can choose a pin again with `annixion-nixpkgs-cooldown`.

Next, the installer lists the available disks and asks which one to use. It always asks, including when you provide `--user-config`, because the configuration describes the system—it doesn’t select the disk. Review the disk selection carefully: the installer asks for confirmation before wiping the chosen disk.

The remaining steps are:

1. Choose whether to encrypt the root partition with LUKS2. Encryption is enabled by default. The installer uses AES-256-XTS and an Argon2id passphrase KDF. Unlocking typically takes about 10–15 seconds.
2. If you enable encryption, enter a passphrase. You’ll need to enter it at every boot. The boot prompt uses the console’s default US keymap, regardless of the keyboard layout selected for the installed system.
3. The installer clears existing mounts, swap, and disk signatures so a previous incomplete install won’t prevent a clean restart.
4. It creates a GPT layout with a 512 MiB EFI System Partition and a root partition using the remaining space.
5. It formats the EFI partition as FAT32. If encryption is enabled, the root partition is formatted as LUKS2 with ext4 inside it; otherwise, it uses ext4 directly. The EFI partition is not encrypted and contains the bootloader, kernel, and initrd.
6. It moves the configuration into `~/.dotfiles`, the location expected by the system’s wallpaper, icon, and certificate references.
7. It generates `hardware-configuration.nix` for the machine. If encryption is enabled, the installer checks that the file contains a `boot.initrd.luks.devices` entry before continuing.
8. It runs `nixos-install --flake ~/.dotfiles#AnNIXion` and hands the dotfiles to the `operator` user.
9. It offers to reboot.

> **Note:** Security tools such as Metasploit and Ghidra are large. On a slow connection, allow 30–60 minutes for installation.

## Option B: Install on an existing NixOS system

Use this option if you already have NixOS with flakes enabled.

Clone the repository and add your machine’s hardware configuration:

```bash
git clone https://github.com/Pyth3rEx/AnNIXion ~/.dotfiles
cd ~/.dotfiles

cp /etc/nixos/hardware-configuration.nix ./hardware-configuration.nix
git add ./hardware-configuration.nix -f
```

`hardware-configuration.nix` is required by the flake. It is gitignored; force-adding it makes it available to the local flake without making it part of your usual tracked files.

### Set the OS account password

This path skips the `annixion-install` wizard, so it doesn’t set an account password for you. The system requires one to evaluate. Generate a password hash:

```bash
nix shell nixpkgs#mkpasswd -c mkpasswd -m sha-512
```

Paste the result into `users.users.operator.hashedPassword` in `user/configuration.nix`.

### Set up SysReptor’s password

SysReptor uses a separate password hash. For the first build, leave this setting empty in `user/configuration.nix`:

```nix
annixion.sysreptor.hashedPassword = "";
```

This creates no SysReptor account yet. After the first switch, generate the hash:

```bash
sysreptor hash
```

Add it to `user/configuration.nix` and rebuild. See [SysReptor setup](sysreptor.md).

### Enable flakes and apply the configuration

If flakes aren’t already enabled, add this to `/etc/nixos/configuration.nix`:

```nix
nix.settings.experimental-features = [ "nix-command" "flakes" ];
```

Then update the flake inputs and apply the configuration:

```bash
nix flake update
sudo nixos-rebuild switch --flake .#AnNIXion --impure
```

After the first successful build, these shell aliases are available:

| Alias | What it does |
|---|---|
| `rebuild` | Applies the current configuration without changing package versions |
| `upgrade` | Updates all flake inputs, then rebuilds |
| `update` | Updates flake inputs without rebuilding |

See the [Zsh reference](zsh.md) for the full list of shell shortcuts and aliases.

## Hyper-V Enhanced Session

**<u>THIS WILL GET DROPPED AS OF 0.6 RELEASE → SWITCHING TO VMWARE</u>**

If deploying on Hyper-V, run this on the Windows host, then fully shut down the VM and reconnect:

```powershell
Set-VM -VMName "AnNIXion" -EnhancedSessionTransportType HvSocket
Set-VMHost -EnableEnhancedSessionMode $true
```

Full clipboard, audio, and dynamic resolution will be available after reconnecting from Hyper-V Manager.

### Audio

Hyper-V emulates no sound card, so the guest has no audio hardware. Sound reaches the Windows host over xrdp’s redirection channel instead, which `system/xrdp.nix` enables with `services.xrdp.audio.enable`.

That channel works through PulseAudio. xrdp redirects audio using `module-xrdp-sink` and `module-xrdp-source`, native PulseAudio modules. `pipewire-pulse` reimplements the PulseAudio protocol but cannot load them, and no PipeWire equivalent is packaged. The Hyper-V profile therefore disables PipeWire and runs PulseAudio, overriding the flake default. With no sound card in the guest, there’s no audio device for PipeWire to manage.

Audio is available inside an Enhanced Session when the connection is configured to play the guest’s audio on the host. See the [FAQ](faq.md#i-have-no-audio-in-the-guest). A plain RDP or console login has no redirection channel, so the guest shows no audio device there.
